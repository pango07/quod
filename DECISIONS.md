- 2026-10-30: T12 0a numbers (Docker Desktop, arm64, 18 cores): overhead +25.7% median (target 10%); FUSE during execution is ~+11% and the output diff (storing ~900 MB of Go build cache per miss) another ~+11%. Hit rate 12/50 commits, 10.8% saved. Full report: docs/bench/0a-cli-cli-arm64.md.
- 2026-10-30: exp/misses, the output tax. Overlay::finish moves output files into the CAS instead of copying them (Cas::take_files): hash every file in place, one syncfs(2) of the store's filesystem, then rename each new file to its blob path. The flush precedes the renames, so a blob name still never points at bytes that are not on disk (the guarantee put_file gets from fsync-then-rename), and the result is written only after that: one flush instead of one fsync per blob (~7k per cli/cli miss: Go rewrites every cache entry file). Blobs get mode 0644 however they arrived; across filesystems a file falls back to put_file. Measured on a loaded box with the base and new binaries interleaved: output diff 3.4-3.6s -> 0.8-1.4s with the CAS populated (steady state, ~3 MB new per miss), 2.6s -> 0.6s with it empty (840 MB new). What remains is the overlay unmount's own writeback of the ~840 MB Go wrote (0.3-0.5s, inherent to writing it) and hashing it (~0.3s); not fsyncs.
- 2026-10-30: exp/misses, warm state (`stillpass run --warm`, default off). The Go build cache earlier warm runs left behind persists as a host directory, <state>/warm/<image>/gocache, bound over GOCACHE inside the sandbox on top of the overlay. It is not observed, not an output and never copied: no materialization in, no 900 MB diff out. Warm runs use their own step key (the env differs, see below), so warm and cold results never share manifests.
- 2026-10-30: Warm state is kept out of the observed tree on purpose. Served through FUSE as part of the tree, every cache probe would be an input: an identical-tree re-run would miss on the `a` entries the previous run turned into files, Go's used() would chtimes and so copy up every entry it used, and Go's trim would see epoch mtimes and delete the lot.
- 2026-10-30: Warm safety argument, in two parts. (1) Results: Go's build cache is content-addressed (action id = hash of source file contents, tool ids, flags, dependency outputs), so a correct cache changes timing, never results; Stillpass cannot discharge "correct" itself (a Go bug that leaves an input out of an action id is invisible to it), which is the spec's position: the tool makes warm state correct, audit catches it lying. (2) Inputs: the manifest of a warm run must cover everything a run with an empty cache reads, or the cache hides inputs from the observer (under-recording). Go has two caches that break (2) because they are keyed by path or mtime, not content, and the warm env turns both off. The module index: file lists and build constraints of every module in GOMODCACHE, cached in GOCACHE keyed by the module's path on the assumption that the module cache is immutable; with it on, a warm cli/cli run recorded 7,101 inputs against 21,049 with an empty cache (GODEBUG=goindex=0 turns it off). The test-result cache: decides "inputs unchanged" from size and mtime, and the observer serves one constant mtime, so a changed fixture of the same size would replay a stale result (GOFLAGS gains -count=1). The acceptance suite audits both parts on every run: W1-W3 compare warm against cold results on the same tree and after a one-file change; W4 asserts every entry of the empty-cache manifest is covered by the full-cache manifest, where an `a` entry counts as covered when its parent directory is recorded as `d` (a matching listing implies the name is still absent).
- 2026-10-30: With goindex=0 the warm env records 9,046 inputs on cli/cli with an empty cache and 9,023 with a full one. The 23 are the assembler's `#include "textflag.h"` probes beside .s files in the module cache, which do not happen when the asm action is cached; each parent directory is listed in both, so W4 counts them as covered. The cold env records 21,051: Go's module indexer walks every module in full (`.github`, `testdata`, nested go.mod probes: 12k entries that are inputs of the index, not of the build), and with test caching on, go test lstats every child of every directory a test opened to hash the test's inputs. Both are over-recording in cold mode, harmless but worth knowing: turning the indexer off in cold mode too would shrink cold manifests by more than half (a Schemas env change, not done here).
- 2026-10-30: W4 found a third path-keyed cache on the first full acceptance run: go test caches each package's vet verdict (vetx, stdout) keyed by the vet tool, its flags and the package's compile action id, whose file list is the compiled files; but vet's buildtag analyzer also parses the package's ignored files (excluded by a GOOS/GOARCH filename suffix, which nothing else opens), so with a full cache 18 such cli/cli files (`flock_windows.go`, `embed_darwin_amd64.go`, ...) vanished from the manifest, and a malformed build constraint added to one would fail cold and pass warm. Go's key is incomplete there; there is no flag to run vet uncached without -a. Answer: over-record. Warm runs add a read of every Go-toolchain source file (go/build's extension set, sp_key::go_source_file) in every directory the step listed (sp_manifest::record_children), the set a cached verdict can stand in for. Not applied to cold runs, which read them anyway. A3 is unaffected: README.md is not a source file.
- 2026-10-30: Warm-mode outputs exclude GOCACHE (it is Stillpass-managed state, as ~/.cache/go-build is on a GitHub runner, not a step artifact); the bind mount's directory appears as one empty `d` output. Everything else a step writes is recorded and replays as before.
- 2026-10-30: Overhead experiment (exp/overhead). Where the execution-phase cost goes, measured by request counts (the observer now counts requests and reports them in an `observer` event; `stat -f <mount>` logs a snapshot) and per-op probes: one `go test ./...` on cli/cli sends ~86k synchronous FUSE requests (45k open, 21k lookup, 20k readdir, 1 getattr) and each round trip costs 50-80 µs on this VM; `go list -deps -test ./...` (Go's serial loading phase) takes 0.7s on ext4 and 2.2-2.6s on the FUSE mount. Overlayfs itself costs nothing measurable (a plain-ext4 lower under the same overlay matched the plain baseline). Request latency, not data copying or the daemon's CPU, is the overhead.
- 2026-10-30: FUSE passthrough (Linux 6.9+, `CONFIG_FUSE_PASSTHROUGH`, CAP_SYS_ADMIN): on open the observer registers the blob as a backing file (one backing id per inode, kept until unmount) and the kernel reads it directly; no READ ever reaches userspace. The open is still a request, and the open is what the log needs, so completeness is unchanged. `max_stack_depth` is 1: blobs must be on a plain filesystem and overlayfs may stack on the mount. If registering fails (no capability, CAS on a stacked fs) the observer falls back to userspace reads for the rest of the mount, with a warning. Verified by an integration test (zero reads with passthrough, same log either way) and A7/A7b.
- 2026-10-30: Init flags: FUSE_PARALLEL_DIROPS, FUSE_CACHE_SYMLINKS and FUSE_NO_OPENDIR_SUPPORT (opendir carries no information; readdir still logs d). Rejected after measuring: FUSE_NO_OPEN_SUPPORT (excludes passthrough, no gain), nicer worker threads (no gain), pre-warming blobs (no clear gain), replying FOPEN_CACHE_DIR from opendir (repeat listings then cost zero readdirs, but every listing costs an opendir; with ~2 listings per directory the round trips come out even). The kernel's default FOPEN_CACHE_DIR for no-opendir handles does not cache on this kernel.
- 2026-10-30: The module cache is sealed. `.stillpass/gomod` (GOMODCACHE, derived from the step env) held 18,925 of the 21,051 manifest entries and nine tenths of the requests; its module@version directories never change once extracted. The sandbox binds a read-only snapshot of it over the merged view, `gomod/cache` (where go writes) is bound back from the overlay so it stays observed, and at unmount every tree entry under the prefix except the carve-out is appended to the log. Over-records by construction: any content, mode, target, addition or removal under the prefix changes a recorded f, l or d entry, so absent lookups there need no separate record. Hit semantics: a module-cache change now always misses, which on this repo coincides with go.mod changing (always read). Manifests grow from ~21k to ~29k entries. STILLPASS_SEAL_MODCACHE=0 disables sealing (bench attribution).
- 2026-10-30: `stillpass bench --interleave` alternates series run by run and `--extra-series NAME=VALUE[,...]` adds observed series with that environment, so load from elsewhere on the box hits every series alike and one run attributes the overhead. Two other agents shared the 18 cores during this work (load averages of 30-65); medians are unreliable there and the per-series minimum or the quiet rounds are the better estimators.
- 2026-10-31: exp/misses acceptance on cli/cli (scripts/acceptance.sh, box shared with two other agents): A1-A7 pass, A7 0 false hits over 12,480 f + 4,548 d + 4,024 a mutations, A7b 10/10, W1-W3 pass, W4 9,536 inputs with an empty warm cache against 9,531 with a full one, the 5 being asm include probes covered by their parent listing, 0 hidden. One earlier full run failed A7b sample 10 (fresh exit 1, replay 0) on docs/testing.md; that run's evidence was lost with the temp state, so the claim "flaky test" rested on one re-run. With the evidence-keeping A7b (review fix), the gate run mutated docs/testing.md three more times: each fresh execution exited 0 with the replay's output, and each fresh manifest had exactly the replayed manifest's 21,052 paths, none of them docs/testing.md (so did all ten sampled files). That is what was observed: four fresh executions agree with the replay and read exactly what it recorded; the one failure left no manifest to compare, and nothing since reproduces it. The suite now writes both logs and both manifests before any A7b assertion fires, so a next occurrence is diagnosable. Miss latency, one-file change to api/client.go, cold vs --warm interleaved: 20.7s vs 9.2s median (0.45x); full numbers in docs/bench/0a-misses-arm64.md.
- 2026-10-31: Review fixes (adversarial read of exp/misses). Step key schema v2: the canonical key JSON gains `warm` (bool, always present, sorted after `v`), so a warm step is a different key by construction and not only because the warm env differs from the cold one (which held only because a cold run cannot override GOFLAGS); goldens regenerated (11 cases, one warm). spike_warm merges `-count=1` and `goindex=0` into the step's own GOFLAGS and GODEBUG (a GODEBUG the user set is kept and extended) and refuses, with KeyError::WarmConflict, a step that sets the same knob to another value; it never silently overrides.
- 2026-10-31: Cas::take_files guards the move. Its soundness rests on nothing writing to the upper dir after the step (bwrap is pid 1 of the sandbox's pid namespace, so its exit kills every sandbox process before run() returns; umount2 without MNT_DETACH fails with EBUSY while anything holds the merged dir), now documented on Overlay::finish and checked: each file's inode, size and mtime are taken before hashing and must be unchanged after hashing and on the blob after the rename, else the blob is removed and the run fails with CasError::Changed, recording nothing (import_dir trusts has(), so a poisoned blob would be a permanent false-hit vector). Hard-linked files are copied, not moved; two new files with equal content move once.
- 2026-10-31: A7b keeps its evidence. On any disagreement between the replay and the fresh execution (exit code, output, or the set of paths read) both logs, both manifests and their diff are written outside the temp state (STILLPASS_EVIDENCE_DIR, default target/acceptance-evidence) before the assertion fires, and every sample now also checks that the fresh manifest does not name the mutated path and reads the same paths as the replayed manifest: a real under-record looks exactly like a flaky test, and the distinction is in the manifests. STILLPASS_A7B_EXTRA=path,... re-runs named files.
- 2026-10-31: exp/overhead result. Execution-phase overhead over the plain baseline, same interleaved run, quiet rounds: original observer +13.4%, passthrough alone +10.2%, passthrough plus sealed module cache +6.4% (plain 17.2s, final 18.3s). Overlayfs is free; the remaining ~1.1s is ~10k round trips for the repo's own sources and gomod/cache. Acceptance with the final observer: A1-A7 pass, A7 0 false hits over 29,879 entries, A7b 10/10. Report: docs/bench/0a-cli-cli-arm64-exp-overhead.md. Next lever is the round trip itself (FUSE over io_uring: this kernel has CONFIG_FUSE_IO_URING, fuser 0.18 does not), or recording the repo's listings and headers once per directory instead of per request.
- 2026-10-31: Review fix (critical): the first sealing bound the repo's live module cache, so a change to it between import and step end would have let the manifest claim X while the step read X'. The snapshot is now `Cas::link_entries`: every blob hard-linked into `<run>/sealed` (one syscall per file, ~26k for cli/cli), each blob's mode set to the entry's, a second mode for the same content copied instead of linked, the carve-out an empty directory to mount over. The store never writes into an existing blob, so the step can only see the imported content; `Cas` and the run dir must share a filesystem (else EXDEV), in which case the module cache is simply observed like everything else, with a warning. Test: a file changed mid-step is neither seen by the step nor recorded, and the next run misses on it.
- 2026-10-31: Review fix (major): passthrough mode is decided once, at the first open, for the whole mount. The kernel refuses to open an inode cached while it has passthrough handles (and vice versa) with an error the daemon never sees; had the observer switched modes after a registration failure, the step could have failed silently and the failure been memoized. Now a registration failure after the first open is an I/O error (EIO to the step, the run is a Stillpass error); a failure at the first open means userspace reads for the whole mount.
- 2026-10-31: The run event carries `observer` (`fuse`, `+passthrough`, `+sealed`) so bench numbers stay attributable to the mechanism that produced them.
- 2026-10-31: exp/overhead rebased onto main (exp/misses merged). The warm GOCACHE bind and the sealed module cache are disjoint subtrees over the overlay; the log is extended with the sealed entries first, then record_children. Acceptance with sealing on: A1-A7, A7b 10/10 and W1-W4 pass. Combined bench (plain vs final observer, 8 interleaved runs, load average 20-54): wall +21.4%, execution +10.3% over all runs; the one quiet round +11% wall with execution equal to plain. Output diff 0.79s (was 1.99s); the module-cache snapshot adds ~0.3-0.9s to the mount phase (22k hard links), a cost to revisit (link once per CAS tree and reuse, or snapshot only the directories go lists).
- 2026-10-31: exp/overhead2, snapshots are shared. The module-cache snapshot cost ~0.9s per run though the sealed prefix is a pure function of its subtree. Snapshots now live in `<state>/snapshots/<key>`, keyed by a BLAKE3 over every entry's path, kind, hash, mode and target; built under a temporary name and renamed into place (a partial build is never visible under a key), directories read-only, reused across runs and commits; gc keeps the four most recently used and removes partial builds older than an hour. Measured: 778ms to build 26,637 entries at load 7, 3ms to reuse. The key covers everything the step can see, so two trees share a snapshot only when their sealed subtrees are identical, and the carve-out's contents are outside both the key and the snapshot.
- 2026-10-31: Blobs are 0444 and never chmod'ed. A hard link shares its inode's mode and one blob may be linked from several snapshots, so a snapshot that changed a blob's mode would change another snapshot's view. The store now gives every blob 0444 (immutable, readable by all, and the mode the Go module cache gives its files, so those link); `link_entries` links a file only when the blob's mode is the entry's and copies otherwise. Tests: two snapshots sharing a blob with different modes each show their own and the blob's mode is unchanged; any difference under the prefix is another snapshot and leaves the first untouched; partial builds are never used.
- 2026-10-31: Snapshots live in the store (`<cas>/snapshots`): they are hard links into it, so the same filesystem by construction, and every state dir and bench run sharing the store shares them. Round-2 paired bench (plain vs final observer, 8 interleaved runs, steady load 19-31 in rounds 2-6): wall +18.9%, execution +9.6% over all runs (15.26s vs 18.14s; execution 16.73s); rounds 2-6 +18% / +8.5%; mount 0.04s, output diff 0.64s. Acceptance with sealing on: A1-A7, A7b 10/10, W1-W4 pass. What remains is the round trip of the ~10k requests the repo's own sources and gomod/cache still send, which the io_uring probe cuts 4.4x.
- 2026-10-31: FUSE over io_uring is feasible on this kernel and is the next lever. `crates/sp-uring-probe` is a minimal read-only FUSE server with the classic /dev/fuse loop and the ring transport (one pinned queue per CPU, REGISTER then COMMIT_AND_FETCH; forgets and interrupts still arrive over the device). Same server, fresh mount per run, three rounds at load 1.5-8: stat of 10k paths 0.35s classic vs 0.08s ring (ext4 0.01s); cat of 10k files 1.08s vs 0.23s (0.07s); ls -R of the module cache 0.50s vs 0.09s (0.01s); go list -deps -test ./... 3.05s vs 0.81s (0.51s). About 4.4x per request; Go's serial loading phase goes from +2.5s over ext4 to +0.3s. Not in the observer yet: fuser 0.18 has no ring transport, so the integration is either a ring transport in fuser (reassemble the split header/op/payload into its contiguous request buffer, commit instead of write) or an in-house low-level server grown from the probe (needs passthrough's backing-id ioctl and open_out size for API 7.45). New dependency io-uring 0.7 for the probe only; `enable_uring` must be set (module parameter, default off).
- 2026-10-31: Review fixes for exp/overhead2 (adversarial read). (1) A snapshot is complete only with its `.complete` marker, written after `syncfs` of the store and before the publishing rename; `ensure` treats a key directory without the marker as absent, renames it out of the way and rebuilds under a new temporary name, so a crash mid-gc or mid-build can never leave something a later run mistakes for a snapshot (the failure mode was a torn module cache, `go test` failing under GOPROXY=off, and `sealed_accesses` recording the full tree: a memoized failure, a permanent false hit). gc also renames a snapshot to `tmp.gc.<key>.<random>` before deleting it. (2) Every user holds a shared `flock` on `<root>/<key>.lock` from `ensure` through unmount (the `Snapshot` carries the file); gc takes the exclusive lock without waiting and skips busy snapshots, re-checking the lock file's inode after locking so an unlinked lock guards nothing. Test: a held snapshot survives gc, and goes once released. (3) gc never fails a run: every problem is a warning, and entries that vanish under it are skipped. (4) The key is versioned (`stillpass snapshot key v1`) and every variable field is length-prefixed, so a symlink target cannot run into the next entry. (5) `syncfs` before the marker, the marker fsynced, the directory fsynced. (6) Temporary names carry 8 random bytes from /dev/urandom, not the pid (pid namespaces sharing a volume reuse pids). (7) Blobs are protected by the read-only bind (MS_RDONLY gives EROFS to everyone, including the root-mapped step user) and by the store never writing into an existing blob; 0444 is the convention that lets snapshots hard-link. A store written before this convention has 0644 blobs and `link_entries` copies all of them once per snapshot (a perf cliff, not a correctness issue); a one-time `chmod 0444` of the store's blobs restores linking. (8) The bench records the load average before and after every run. (9) The io_uring probe is excluded from the workspace and builds on its own, so CI and lint never build io-uring; its queue threads keep the buffers alive past the ring. (10) `enable_uring` is reported by check-host.sh as optional: `echo Y > /sys/module/fuse/parameters/enable_uring`, root, not kept across a reboot or a Docker Desktop VM restart; without it the observer uses the classic transport.
- 2026-10-31: exp/polyglot. Everything Go-specific moves out of generic code into a toolchain profile (`sp_key::profile`): the step env, the dependency-install step, the sealed prefixes and their carve-outs, warm state and its cache-disabling knobs, the over-record rule, the acceptance suite's file picks (source extensions, comment syntax, test-file patterns), and the directories a step must never write under. Go, Node and Python are three values of one shape; `run.rs`, `bench.rs`, `seal.rs` and the acceptance suite consult the profile and know no language. The toolchain is detected from the repo's top level (go.mod, package.json, pyproject.toml/setup.py/setup.cfg/requirements.txt/tox.ini); a repo with markers for several needs `--toolchain`, guessing would run the wrong env; a repo with none runs under Go's profile, the env every step had before profiles (the rootfs suite's marker-less fixtures). The split driver (exp/split) is the one profile slot left empty.
- 2026-10-31: Step key schema v4 (first written as v3; exp/rootfs, merged first, took v3): the canonical key JSON gains `toolchain` (go, node, python), sorted after `roots`, so a step under another profile is another key by construction and not only because the env lists differ. Goldens regenerated (20 cases: rootfs's 13 built from Go steps, 2 Node, 2 Python, 3 hand-built). The Go env is byte-for-byte the handoff's Schemas list; nothing was added to it (`CI=true`, which Node and Python get because Actions sets it and Jest reads it as `--ci`, would have been an unaudited change to the Go manifests).
- 2026-10-31: Sealing is generic (`crates/sp-cli/src/seal.rs`): a profile names prefixes (an env variable's directory, or every directory of a given name not nested in another, for monorepos) and carve-outs under them where the tool writes. Carve-outs are in the snapshot as empty directories whether or not the tree has them (the key is the same either way; they are mount points) and are created in the merged dir before the step so the writable bind has a source. - 2026-10-31: Proof streaks are per (step key, manifest). The alternative reading ("N consecutive executions of the key") would reset the streak on every intervening tree and never compare Monday's run of tree A with Tuesday's: the per-manifest streak compares exactly the runs whose inputs were identical, which is where a hidden input shows.
