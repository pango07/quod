# Troubleshooting and FAQ

Most questions are answered by the `quod vitest:` lines in your test job's log. Start there.

## Why did every file run?

Look for these in the test step's log, in this order:

### Every file ran right after upgrading

The first run or two after you upgrade the action run every file. That's expected, and it settles by itself:

1. **The first run** uses a newer Quod release, and recordings are tied to the release that made them, so every file runs and is recorded.
2. **The second run** is the second witness for those records. Each record is provisional until a second run agrees with it, so the files run again. The log says so:

```txt
quod vitest: second witness: 280 provisional records run again (2 witnesses needed)
```

From the third run on, unchanged files replay. The same thing happens, file by file, after any change: a file that changed runs on that commit, and once more on the next run to collect its second witness.

### There was no recording yet

```txt
Quod: no recording yet; every test file runs and records
```

The first run on a repository always runs everything. So does a branch whose base has never been recorded. Records are saved from writer branches, such as pushes to `main`. A pull request records only for its own branch. If you've set `record: false`, check that the `quod-shadow` job ran and finished after a push to a writer branch.

### A shared input changed

```txt
quod vitest:   shared input changed: f:vitest.config.ts
```

Some inputs belong to every test file: your vitest config and anything it imports, `tsconfig`, plugins, setup files, the packages vite and vitest load (for example a vite, vitest or jsdom upgrade), and directory globs that vite runs. When one changes, every file runs and is recorded again, and then runs once more on the next run for its second witness.

<Tip>
  If a generated file shows up here on every push, such as a build stamp or a file that embeds a timestamp, make its output deterministic, or keep it out of what the config imports.
</Tip>

### A tool version changed

A recording is tied to the Node, vitest and Quod versions that made it. A new Node patch release, a vitest upgrade or a new Quod release means one full run.

<Tip>
  `node-version: 24` follows the latest Node 24 release. Pin an exact version, such as `node-version: 24.11.0`, if you'd rather choose when that full run happens.
</Tip>

### The vitest arguments changed

vitest's arguments are part of the key, because a filter or option changes what a file's result means. A job that runs `vitest run --project unit` and one that runs `vitest run` keep separate recordings. Output-only flags like `--reporter` don't count.

### Quod stepped aside

If there are no `quod vitest:` lines at all, Quod didn't run, and vitest ran plain. That happens when:

- `QUOD_DISABLE=1` is set
- the runner isn't Linux x64
- the action couldn't set up (the log says *Quod is off for this job* and why)
- vitest ran in watch mode or with `--coverage`, `--shard`, `--changed`, `-u` or another flag Quod leaves alone ([full list](/docs/supported-setups#vitest))
- the action line comes **before** `actions/setup-node` (it needs `node` on `PATH`)

## Why does this one file always run?

The log lists files that can't be recorded:

```txt
quod vitest:   3 files always run: …
```

A file always runs if it starts a child process, uses the network, writes into the repository, or reads a per-run CI value like `GITHUB_SHA`. The [Make it even faster](/docs/faster#dont-read-per-run-values-in-tests) page shows how to fix each one. On the Trust page in Quod Cloud, these files show as **Always runs**, with the reason.

A file can also run because it's **paused**: an audit found a different result, or a second run disagreed with its record. It replays again once enough runs in a row agree with it (see [`QUOD_VITEST_REPROVE`](/docs/reference/environment-variables#quod_vitest_reprove)).

A file that fails only while being recorded also keeps running. Quod runs it again without recording, so the job stays green, but it isn't recorded. The log shows:

```txt
quod vitest: 1 files failed while recording; running them again without recording
quod vitest: without recording, the run passes
```

That usually points at a test that depends on timing. Recording slows a test down a little, which can push a tight timeout over the edge.

## How do I force a full run?

Set `QUOD_VITEST_FULL=1`. Every file runs, and is recorded again.

```yaml title=".github/workflows/ci.yml"
env:
  QUOD_VITEST_FULL: 1
```

<Tip>
  To force a full run on demand, add a `workflow_dispatch` trigger whose input sets this variable.
</Tip>

## How do I turn it off?

Set `QUOD_DISABLE: 1` in the workflow's or the job's `env`. vitest runs plain, your install runs as always, and nothing else changes. To remove Quod, delete the action line.

### Turn off inline recording

To keep recording out of your test job, set `record: false`. The test job then only reads the ledger and replays, as in v1, and records nothing. Use this if you keep the older shadow job as your recorder:

```yaml title=".github/workflows/ci.yml"
      - uses: pango07/quod-action@991753ca6f46d81b184604673dfd247e66a9476e # v2
        with:
          record: false
```

Without a shadow job, nothing records, so nothing new replays. You can also turn off just the dependency cache (`dependencies: false`) or the turbo/Nx remote cache (`task-cache: false`). See [the action's inputs](/docs/reference/action#turning-parts-off).

## FAQ

### Can Quod change my test results?

No. Replayed files report their recorded results through vitest's own reporters. A record replays only after two independent runs gave the same result for every test, and failures are never replayed. If recording makes a file fail, Quod runs it again without recording, and that plain run decides the job's result. So Quod never turns a green job red.

### What about flaky tests?

A failure always runs again. A flaky file has to pass twice in a row, on the same inputs, before it's replayed, and if the two runs disagree it's paused. A file that passed twice can still be replayed as passing while its inputs are unchanged. When an audit runs it and gets a different result, the file is paused and runs every time until it's consistent again.

### What if Quod Cloud is down?

If the server doesn't answer, or gives the job no ledger, Quod uses the copy of the ledger in the GitHub Actions cache. The action sets [`QUOD_VITEST_CLOUD_FALLBACK`](/docs/reference/environment-variables#quod_vitest_cloud_fallback) for this. If there's no usable ledger at all, files simply run. The turbo/Nx remote cache is off for that job, so tasks run as always. Quod never fails your job by itself.

### Does Quod add runner minutes?

No second job: Quod records in your test job, as it runs. Recording adds some overhead to the files that run, and a file that changed runs once more on the next run for its second witness. Across our end-to-end benchmarks, CI cost through the action was 0.70× to 0.82× of plain CI. See the [headline numbers](/docs#headline-numbers).

### Can a pull request poison the results main uses?

No. A pull request's job can only write recordings for its own ref, and no other branch reads those. Pull requests from forks never record. See [Trust and audits](/docs/trust).

### What does Quod Cloud store?

For each suite: the ledger (each test file's input keys, such as paths, content hashes and package versions, and its per-test results), the recorded vitest output used for replays, and copies of the source files your tests reached. Function-level narrowing compares a file's recorded version with the current one, which is why those copies are kept.

Quod keeps GitHub's OIDC request token and server tokens away from vitest, so tests never see them, and it refuses to upload a ledger that contains one.
