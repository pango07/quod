# Introduction

Quod makes CI faster by not re-running tests whose inputs haven't changed. When a test file and everything it depends on are the same as the last time it passed, Quod reports that result again instead of running it.

## What Quod does

Most commits touch a few files, yet CI runs every test on every push. Quod watches what each test file actually reads while it runs: source modules, fixtures, config, packages, environment variables. On the next run it checks those inputs. Eligible, verified test files can be **replayed** when their recorded inputs match. Changed and ineligible files execute; confirmations and audits can also execute unchanged files. Replayed outcomes are included in the test summary and reports.

You keep your workflow. Quod is one line after `actions/setup-node`, and it hooks into the `vitest run` your job already starts, whether that's through `npm test`, `npx`, `pnpm`, or `turbo`. The same line restores your dependencies before your install step and, if you use turbo or Nx without a remote cache of your own, points their remote cache at Quod Cloud.

<Note>
  Quod works with **vitest** today. pytest and Go are experimental. See [Supported setups](/docs/supported-setups).
</Note>

## How it stays correct

A replayed result is useful only when it agrees with a fresh execution. Quod uses input checks, confirmations and audits to establish evidence for reuse:

- **Inputs are observed, not guessed.** Each test file's dependencies come from what it actually read during a real run, not from a config file or an import scan. If Quod can't follow something a file does, such as starting a child process, using the network, or writing into the repository, that file always runs.
- **Failures never replay.** Only a file that passed (or was skipped) can be replayed.
- **Two runs must agree.** A file is recorded in your test job as it runs, but its record replays only after a second, independent run of the same inputs gives the same result for every test. A run that disagrees quarantines the file.
- **Plain retries check recording failures.** If a file fails while being recorded, Quod can run it again without recording and use that result. Recording still adds overhead and may affect timing-sensitive tests.
- **Audits run replays for real.** When workers would otherwise sit idle, a random sample of replayable files runs instead of replaying, and is compared with the recording, test by test. A mismatch stops that file replaying.
- **Only trusted branches write.** Pull requests read results recorded on your writer branches, such as `main`, but they can't write them. See [Trust and audits](/docs/trust).

## Observed whole-job savings

We compared plain CI with Quod across the same 12 commits of **convex-helpers**, including the cold start, installs, builds, tests, confirmations, audits and Action overhead.

| Measure | Plain | Quod | Reduction |
| --- | ---: | ---: | ---: |
| Total runner time | 1,766 s | 968 s | **45.2%** |
| Per-job rounded minutes | 36 | 21 | **41.7%** |
| Observed wrong results | — | 0 on every commit | — |

The rounded-minute reduction estimates runner charges at the same per-minute rate. The public jobs cost $0. This excludes Quod pricing, storage and account allowances; it is not a measured reduction in a customer's total bill. Time and cost savings describe the same work and must not be added together.

Separate warm-hit probes had a best job of **14 seconds against an 11-second empty job: floor + 3 seconds**. The median of three probes was **20 seconds**. These probes are excluded from the 12-commit totals.

<Note>
  These results use an experimental Action with lineage witnesses and a bounded configuration-input proof enabled, and timing-sensitive replay off. They are not the released Action's defaults or a savings guarantee. First recordings, shared input changes and audits can make individual jobs slower. Zero observed wrong results is evidence for this window, not proof of universal correctness.
</Note>
